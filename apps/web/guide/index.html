Foundation

What exactly is HarnessLab?

A guided platform for deciding what to build, how much agency to use, and how to keep the system dependable.

1

Plain English

  • A coach for AI and agent design.
  • Turns a fuzzy use case into a clear, testable plan.
  • Points out missing details, contradictions, and risky assumptions.
  • Explains whether you need ordinary software, a workflow, one agent, temporary subagents, or A2A.

  • Browser-first product with deterministic analysis and typed result contracts.
  • Requirement intelligence, topology guidance, policy design, and critic review.

A harness is the control system around AI

The model is only one component. The harness controls what enters, what can happen, what must be returned, and how the result is judged.

07
Architecture choice

Architecture decision ladder

Escalate only when the simpler option no longer fits the evidence.

1

Deterministic software

Best for exact rules, transforms, calculations, and predictable logic.

2

LLM feature with deterministic wrapper

One reasoning step inside strict validation, policy, and output shape.

3

Deterministic workflow

A fixed multi-step sequence with known order and low autonomy.

4

Single bounded agent

Useful when the next step depends on observed intermediate results.

5

Orchestrator with temporary subagents

Use only for truly independent parallel workstreams.

6

External A2A network

Use only when separately operated agents exchange tasks and artifacts.

Core decision rules

  • Choose the least-complex topology supported by evidence.
  • Risk adds containment and approval; it never justifies more agency.
  • Temporary subagents should be short-lived, isolated, and disposable.
  • A2A is for real external trust boundaries, not internal helper workers.
  • Upgrade only after evaluation proves the simpler option is insufficient.
✦Architecture is a decision ladder, not a race to the most agentic design.
08
Decision evidence

Nine factors determine how much agency is justified

The decision should be explainable and tied to requirement evidence, not to fashionable architecture.

01

Interpretation uncertainty

Does the task need judgment, comparison, synthesis, or ambiguous-language handling?

02

Deterministic sequence

Can the entire task be expressed as known steps and exact rules?

03

Iteration & recovery

Does the next action depend on intermediate results, failures, or retries?

04

Tool boundaries

Which systems must be accessed, and through which typed operations?

05

Independent parallelism

Can workstreams run independently without sharing mutable state?

06

External trust boundary

Are separately operated agents or organizations exchanging tasks?

07

Risk & reversibility

Could actions change production, expose data, spend money, or affect people?

08

Evidence burden

Must claims be cited, evaluated, independently challenged, or audited?

09

Knowledge requirement

Does the system need documents, policies, history, or freshness-aware retrieval?

Agency benefitmust exceedcoordination + context + evaluation + failure cost

When not to spawn

  • The task is sequential and small.
  • The workers would need constant shared mutable state.
  • The result cannot be validated independently.
  • The extra latency or cost exceeds the expected quality gain.
  • The “specialists” are only decorative personas.
✦Permanent architecture, temporary intelligence. Retain validated artifacts and dispose of worker state.
10
Integration concepts

Tools, MCP, retrieval, and A2A are not the same thing

Choose each one for a different responsibility.

</>

Native typed functions

What it is
Direct code hooks with strict input and output schemas.
Use it when
You need a small known capability inside your own system.
Example
Create a ticket, look up a user, run a calculation.
⌘

MCP

What it is
A standard protocol for model-to-tool and model-to-context access through servers.
Use it when
Capabilities must be reusable, permissioned, discoverable, or standardized.
Example
Connect shared data, documents, and app tools through one interface.
◉

Retrieval

What it is
A service that selects documents or knowledge to ground reasoning.
Use it when
The task depends on policies, manuals, history, or trusted sources.
Example
Bring support documents or policy pages into context.
◎

A2A

What it is
Task and artifact exchange between separately operated agents.
Use it when
There is a real independent-agent boundary across systems or organizations.
Example
Your orchestrator sends a task to a partner-operated agent service.
✦Common pattern: typed functions first → MCP when reusable → retrieval when knowledge is external → A2A only for real cross-agent boundaries.

Information architecture

Context is compiled; knowledge is retained as artifacts

Do not send the entire project to every model or worker. Assemble minimum context per task and preserve durable evidence outside conversations.

Source context

Requirement, policies, approved data references, prior artifacts

→
Context compiler

Whitelist fields, remove secrets, enforce byte limits, attach policy

→
Task envelope

Role, objective, inputs, tools, permissions, timeout, return schema

→
Validated artifact

Claims, evidence, uncertainty, status, lineage, trace references

What survives

  • Requirement assessment
  • Architecture decision
  • Harness specification
  • Worker results
  • Critic findings
  • Trace bundle
  • Evaluation summary

What should not survive by default

  • Raw provider credentials
  • Unbounded chain-of-thought
  • Temporary worker memory
  • Irrelevant project history
  • Unvalidated model prose
  • Hidden tool handles
  • Production action tokens
✦Context isolation: every worker receives only what it needs, while durable decisions live in typed artifacts.

Governance

Autonomy is granted capability by capability

“Autonomous” is not one switch. Each action gets an explicit allow, allowlist, approval, or deny policy.

CapabilityPolicyEnforcement
Read submitted requirementAllow

Always available to the current run.

Read approved context sourcesAllowlist

Source-by-source grant with trace event.

Spawn temporary workersBounded

Maximum count, depth one, timeout, no child spawning.

Write or modify external systemsHuman approval

Separate short-lived action token after named approval.

Production deletion or deploymentDeny

Tool is not exposed in the planning harness.

Paid model usageDeny

Local or explicitly free route until authorized.

1

Least privilege

Expose the smallest capability set.

2

Separate reasoning from action

A plan cannot authorize itself.

3

Make risky actions reversible

Preview, approve, execute, verify.

4

Record evidence

Every permission and action has traceable rationale.

End-user playbook

How to use HarnessLab step by step

A guided journey from a rough idea to a usable, versioned harness plan.

Describe the use case

Write the real problem and desired outcome in plain English.

Good: “Investigate approved KPI data and return a cited root-cause report.”
2

Add context

Name users, inputs, outputs, tools, restrictions, and success criteria.

Avoid naming systems that are not truly required.
3

Check readiness

Review what is covered, partial, missing, or contradictory.

Use the copied question list as your interview checklist.
4

Clarify autonomy, approval, data access, retention, and external access.

Aim for zero high-severity contradictions.
5

Review architecture

Understand why software, workflow, agent, subagents, or A2A was selected.

Prefer the simpler viable option.
6

Inspect protocols & controls

Review tools, MCP, retrieval, A2A, permissions, and denied actions.

7

8

Store the versioned result and move into engineering.

The saved contract becomes the implementation baseline.

Developer playbook

Turn guidance into an implementation-ready build

Translate the retained decisions into layers, interfaces, policies, tests, and deployment seams.

1

Requirement specification

Use case, users, inputs, outputs, constraints, approvals, success criteria.

2

Decision layer

Requirement intelligence, topology decision, protocol guidance, alternatives.

3

Control layer

Typed contracts, policies, budgets, timeouts, state, action tokens, trace events.

4

Execution layer

Deterministic logic first; bounded agent loops only when justified.

5

Integration layer

Typed functions, MCP servers, retrieval, optional A2A, credential isolation.

6

Evaluation layer

Fixtures, critic review, failure injection, regression tests, quality and safety metrics.

Build principles

  • Start with the simplest architecture that fits.
  • Keep inputs and outputs typed.
  • Use local deterministic defaults first.
  • Keep provider credentials server-side only.
  • Validate every artifact at every seam.
  • Preserve traceability for decisions and outputs.
  • Test denied actions and failure modes.
  • Deploy one complete slice before expanding.
Technical note: HarnessLab helps design the harness; it does not replace engineering discipline, threat modeling, or production validation.

Worked example

Telecom KPI anomaly investigation

See how one vague request becomes a bounded multi-stage harness design.

Original idea
“Build an agent that finds why a KPI dropped.”

After requirement guidance

Investigate approved telecom KPI data from a read-only warehouse, validate freshness and completeness, compare independent dimensions in parallel, and return a cited root-cause report for operations leaders. Never modify production data. Escalate when evidence confidence is below 0.75. Complete within 60 seconds and retain the analysis trace.

Worker 2Diagnostic InvestigatorSegments, drivers, measured contribution

No write capability exposed.
