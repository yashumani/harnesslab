Chapter 01

The three corrections that prevent most caching mistakes

Use these as the mental model for the entire module.

1

Prompt caching does not cache the answer.

The provider reuses the model state for a matching prompt prefix, then processes the changing suffix and generates a fresh answer.

2

KV caching is not a Redis-style database.

The “keys” and “values” are attention tensors derived from model hidden states—not application records such as customer:123.

3

Conversation history is persistence, not automatically caching.

Messages, summaries, and memory must live in an authoritative store if the agent needs them tomorrow.

Chapter 03

What the KV cache actually stores

Each attention layer derives Query, Key, and Value representations. During autoregressive decoding, earlier K and V tensors can be reused.

Conceptual equations 
Kₜ = hidden_stateₜ × Wₖ
Vₜ = hidden_stateₜ × Wᵥ

At step t, the model computes the new token’s K and V once, appends them to the cache, and attends over cached plus current values.

Tensor shape 
[batch, KV heads, sequence length, head dimension]

The cache exists per model layer. Memory grows as context, concurrency, batch size, or numeric precision increases.

Chapter 04

Per-request KV cache versus cross-request prefix cache

They reuse the same kind of model state, but across different boundaries.

Normal KV cache

One request → one ongoing generation

The runtime reuses earlier tokens while producing the next token. The cache may disappear when the request ends.

Prompt→Token 1→Token 2→Token 3
Prefix cache

Earlier request → later request with same beginning

The runtime retains reusable KV blocks and lets another request skip prefill for the identical shared prefix.

Agent instructionsTool definitionsMetric glossaryQuestion A / Question B
Prefix caching improves prefill, not long-output decoding.

If the model must generate 5,000 new tokens, it still has to decode those tokens. Reusing the prefix mainly reduces time and cost before the first output token.

Chapter 05

Prompt caching is hosted prefix reuse

The provider preserves reusable model state for the stable beginning of a request and generates a fresh answer for each call.

  1. 1
    Receive the rendered prompt

    Tools, system/developer instructions, history, retrieved data, and user input form a precise token sequence.

  2. 2
    Process the stable prefix

    The model computes attention state for the reusable beginning.

  3. 3
    Write an eligible cache entry

    The provider retains the reusable state at a breakpoint.

  4. 4
    Match a later prefix

    A later request must share the same rendered beginning through an eligible breakpoint.

  5. 5
    Process only the new suffix

    Current permissions, retrieved values, timestamps, and the new question remain uncached when placed after the boundary.

  6. 6
    Generate a new answer

    Prompt caching never means “return the answer from last time.”

Prompt caching can reduce

  • Repeated input computation
  • Cached-input cost
  • Time to first output token
  • GPU prefill work

Prompt caching does not remove

  • Output-token generation
  • Tool and database latency
  • Context-window accounting
  • Permanent conversation storage
  • The changing part of the request
Chapter 06

Prefix matching is exact, not semantic

A timestamp, request ID, reordered tool schema, or changed earlier message can break reuse after the first changed token.

    Chapter 08

    OpenAI explicit prompt-caching pattern

    The reusable developer content is placed in an input_text block because top-level instructions cannot carry an explicit breakpoint.

    Python · Responses API
    from __future__ import annotations
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

STATIC_AGENT_PREFIX = """
You are the Business Narrative Intelligence Agent.
Explain metric movements, distinguish facts from hypotheses,
respect metric definitions, and never invent unavailable values.

Metric glossary:
[Insert stable glossary here.]

Narrative framework:
[Insert stable narrative rules and examples here.]
"""

def ask_agent(question: str, tenant_id: str) -> str:
    question = question.strip()
    if not question:
        raise ValueError("question cannot be empty")

    response = client.responses.create(
        model="gpt-5.6",
        prompt_cache_key=f"bi-narrative-agent:v1:{tenant_id}",
        prompt_cache_options={"mode": "explicit", "ttl": "30m"},
        input=[
            {
                "role": "developer",
                "content": [{
                    "type": "input_text",
                    "text": STATIC_AGENT_PREFIX,
                    "prompt_cache_breakpoint": {"mode": "explicit"},
                }],
            },
            {
                "role": "user",
                "content": [{"type": "input_text", "text": question}],
            },
        ],
    )

    if response.usage is not None:
        print(response.usage.model_dump())
    return response.output_text
    First request

    Writes the stable prefix when it meets the selected model’s minimum cacheable length.

    Later request

    Can read the matching prefix, process the new question, and generate a fresh answer.

    Observe usage

    Track cached_tokens, cache_write_tokens, total input, latency, and realized cost.

    Prompt-caching economics

    A cache is valuable only when reads repay the write and operational complexity.

    Chapter 10

    Exact response caching can skip the model entirely

    Use it only when every answer-affecting input can be represented in a canonical, versioned identity.

    Tenant+Permission scope+Model+Prompt version+Data snapshot+Question→SHA-256 cache key
    Python · Redis exact cache
    import hashlib
import json
from typing import Any


def canonical_json(value: Any) -> str:
    return json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False)


def build_response_cache_key(
    *,
    tenant_id: str,
    permission_scope_hash: str,
    model: str,
    prompt_version: str,
    data_snapshot_id: str,
    request_payload: dict[str, Any],
) -> str:
    identity = {
        "tenant_id": tenant_id,
        "permission_scope_hash": permission_scope_hash,
        "model": model,
        "prompt_version": prompt_version,
        "data_snapshot_id": data_snapshot_id,
        "request": request_payload,
    }
    digest = hashlib.sha256(canonical_json(identity).encode("utf-8")).hexdigest()
    return f"llm-response:v1:{digest}"
    Must include

    Tenant, permissions, model, prompt/tool/schema versions, question, context, data snapshot, locale, and safety settings when they can change the answer.

    Must not expose

    Raw secrets or sensitive content in visible Redis keys. Hash a canonical payload instead.

    Failure behavior

    Redis failure should normally degrade to a fresh model call. The cache is a disposable optimization, not the source of truth.

    Chapter 11

    Semantic response caching matches meaning—but raises the risk of false hits

    It can be excellent for stable FAQs and dangerous for personalized, current, or action-oriented requests.

    1Embed incoming question
    →
    2Apply hard metadata filters
    →
    3Run similarity search
    →
    4Threshold hit or miss
    →
    5Return cached answer or call model

    Good initial candidates

    • Password-reset instructions
    • Stable product documentation
    • Non-personalized FAQs
    • Approved internal policy explanations

    High-risk candidates

    • Current KPI values
    • Financial balances
    • User-specific permissions
    • Jurisdiction-specific legal answers
    • Inventory, pricing, or action requests
    • Questions dependent on conversation context
    Semantic similarity is never enough.

    Require the same tenant, permission scope, data version, locale, intent type, model/version, safety status, and freshness boundary before considering the vector threshold.

    Chapter 12

    Conversation history is authoritative state

    The model only knows earlier facts when the application sends them again, summarizes them, references a managed conversation, or retrieves long-term memory.

    User · Turn 1

    My preferred market is Northeast.

    User · Turn 2

    Show me churn.

    How does Turn 2 know Turn 1?

    Replay messages · send a summary · use a provider conversation ID · retrieve durable memory

    PostgreSQL / MongoDB

    Messages, summaries, user facts, feedback, audit records, and durable thread metadata.

    Redis with persistence

    Short-lived session state, queues, coordination, rate limits, and optionally durable state when configured accordingly.

    Provider-managed conversations

    Useful convenience, but still evaluate retention, portability, privacy, and source-of-truth requirements.

    RulePrompt caching may make history cheaper to process; it does not make the cache your authoritative memory store.
    Chapter 13

    Tool and retrieval caching often saves more time than model caching

    Agents can repeatedly call warehouses, sheets, internal APIs, vector search, MCP servers, and web services.

    Tool call
    get_metric(
  metric="churn",
  period="2026-07",
  market="Northeast"
)
    Safe key

    tool name + normalized arguments + tenant + permission scope + source-data snapshot + tool version

    Cacheable read operations

    • Read-only metric lookup
    • Static reference data
    • Document chunk retrieval
    • Published reports
    • Short-TTL exchange rates

    Never replay as execution

    • send_email()
    • create_ticket()
    • update_dashboard()
    • delete_file()
    • transfer_money()
    • approve_request()
    Side-effect result ≠ side effect executed.

    Returning the cached result of an earlier write operation would falsely imply that the current action happened. Cache read-only observations, not external mutations.

    Start with semantic answer caching disabled for executive KPI questions. Introduce it later for stable FAQ and documentation intents only after an evaluation set measures false hits.

    Chapter 15

    Invalidation and observability determine whether a cache is trustworthy

    Storing data is easy. Knowing when reuse is no longer valid is the real engineering problem.

    agent_prompt_version = "v7" tool_schema_version = "v3" metric_glossary_version = "2026-08-21" ontology_version = "v12" data_snapshot_id = "2026-08-26T07:45:00Z" permission_scope_hash = "a84..."

    Natural miss or invalidate when

    • Agent instructions change
    • Tool or output schema changes
    • Metric definition or ontology changes
    • Source data refreshes
    • User permissions change
    • Model or reasoning settings change
    • Safety policy or tenant configuration changes

    Production metrics

    • Prompt-cache token hit rate
    • Cache reads per write
    • Exact response-cache hit rate
    • Tool-cache hit rate
    • P50/P95 time to first token
    • Input cost per successful turn
    • Stale-answer and semantic false-hit rates
    • Cross-tenant isolation violations
    • Evictions and memory size
    Prompt-cache token hit ratesum(cached_input_tokens) / sum(total_input_tokens)
    Reads per writenumber_of_cache_reads / number_of_cache_writes
    Exact response hit rateresponse_cache_hits / cacheable_requests
    Operating principleA cache is a disposable optimization, never the source of truth.
    Chapter 16

    Practical experiments and final knowledge check

    Make each distinction observable before implementing production caching.

    A

    Prompt caching

    Use a large stable prefix and three changing questions. Log total input, cached tokens, write tokens, and time to first token.

    Expected: first call writes; later calls read.
    B

    Break the prefix

    Place a changing timestamp at the beginning, then move it after the cache breakpoint.

    Expected: reuse disappears, then returns.
    C

    Exact response cache

    Ask an identical snapshot-bound question twice.

    Expected: second response skips the model.
    D

    Change the data snapshot

    Change the report refresh identifier while keeping the question identical.

    Expected: exact cache miss and fresh answer.
    E

    Self-hosted prefix caching

    Run repeated questions against the same long document with vLLM prefix caching enabled.

    Expected: lower prefill latency, not faster long-output decoding.
